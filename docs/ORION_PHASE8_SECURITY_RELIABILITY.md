# ORION Phase 8 — Production Security, Reliability & Deployment Hardening

## Overview

ORION Phase 8 establishes a hardened operational baseline for the ORION Autonomous AI Execution Platform. Phase 8 does not alter the fundamental multi-agent or SWE architecture delivered in Phases 1–7; rather, it solidifies all ingress boundaries, resource constraints, authorization policies, secret protections, lifecycle shutdown mechanisms, and deployment configurations for production-like environments.

---

## 1. Threat Boundaries & System Trust Model

ORION operates under an explicit asymmetric trust boundary:
* **Frontend / Clients (Untrusted)**: Web browsers, command-line clients, and external API callers are treated as completely untrusted entities. Client state is never authoritative. Clients cannot forge approval decisions, mark tasks verified, or modify evidence ledgers.
* **API Boundary (Authoritative Gatekeeper)**: Validates incoming payloads, bounds body sizes, applies rate limits, scrubs error tracebacks, injects security headers, and enforces canonical route parameter formats.
* **Core Execution Engine (Authoritative Runtime)**: The execution pipeline runs strictly within canonical workspace paths. Tool execution is mediated by `ToolExecutor` and subject to `ToolRiskPolicy` checks.
* **Approval Boundary (`ApprovalService`)**: Mediates sensitive operations (such as code patch applications and privileged tool executions) via capability tokens.
* **Verification Boundary (`VerificationEngine`)**: Formally verifies test results and requirements against the tamper-evident `EvidenceLedger`. Clients cannot mark a mission verified.

## 2. Authentication & Authorization Model

### Capability Approval Tokens
* **Security Primitive**: UUID4 capability approval token with relational context binding.
* **Context Binding**: Each approval request generated by the system binds:
  1. `request_id` (UUID4)
  2. `mission_id` / `task_id` (relational binding)
  3. `action_type` / patch checksum
  4. Decision state (`PENDING`, `APPROVED`, `DENIED`, `EXPIRED`)
  5. Deciding operator identifier and reason.
* **Replay & Tampering Prevention**:
  * Approval tokens can only be decided once (`PENDING` -> `APPROVED`/`DENIED`). Re-deciding or reusing an already decided token raises `ApprovalRequiredError` or validation rejection.
  * Attempting to approve an action with a mismatched mission ID, nonexistent approval ID, or malformed UUID is rejected with HTTP 400 or 404.
  * Approval tokens are never treated or described as cryptographic signatures; they are cryptographically random UUID4 tokens relationally bound to internal domain entities.

## 3. Workspace Security & Containment

* **Canonical Path Resolution**: Workspaces are resolved to absolute canonical paths. Symlink traversals outside the designated root are prohibited.
* **Protected System Path Rejection**: `validate_workspace_path` explicitly forbids pointing workspaces to filesystem roots (e.g. `C:\`, `/`) or operating system directories (`Windows`, `System32`, `Program Files`, `/etc`, `/sys`, `/proc`, `/dev`, `/boot`).
* **Tool Containment**: Tools (e.g., `read_file`, `write_file`, `apply_patch`, `run_tests`) validate all target paths against the workspace boundary. File modifications outside the workspace boundary raise strict access violations.
* **Process Execution Safety**: Test runners and tools execute with explicit arguments (`shell=False`) and enforced timeouts, preventing shell injection and runaway processes.

## 4. API Security, Request Limits & Headers

### Request Size Bounding
* Inbound request bodies are strictly bounded by `max_request_body_bytes` (default 10 MB in production; configurable via `ORION_MAX_REQUEST_BYTES`).
* Requests exceeding this limit are terminated early with `HTTP 413 Payload Too Large` without buffering the body into memory.
* Negative or non-integer `Content-Length` headers return `HTTP 400 Bad Request`.

### HTTP Security Headers
Every HTTP response (API, SSE, and static UI assets) includes hardened security headers:
* `X-Content-Type-Options: nosniff` — Prevents MIME-type sniffing.
* `X-Frame-Options: DENY` — Protects against clickjacking.
* `Referrer-Policy: strict-origin-when-cross-origin` — Protects referrer leakage.
* `Permissions-Policy: geolocation=(), camera=(), microphone=()` — Disables browser sensor capabilities.
* `Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self'` — Restricts execution to first-party origins while allowing the vanilla SSE application to function.
* `Cache-Control: no-store, no-cache, must-revalidate` — Prevents intermediate caching of sensitive API telemetry and mission responses.

## 5. Rate Limiting & Abuse Protection

* **Mechanism**: In-process, thread-safe sliding-window token bucket limiter (`TokenBucketRateLimiter`).
* **Granular Tiers**:
  * **General API**: Default 120 requests/minute per client IP (configurable via `ORION_RATE_LIMIT_PER_MINUTE`).
  * **Mission Submissions**: Default 20 submissions/minute per client IP (configurable via `ORION_MISSION_RATE_LIMIT_PER_MINUTE`).
  * **Health & Readiness**: Exempt from rate limiting to prevent probe flapping during Kubernetes or Docker health monitoring.
* **Response Contract**: Returns `HTTP 429 Too Many Requests` with a calculated `Retry-After` header indicating seconds until the window frees capacity.
* **Bounded Tracking**: Self-pruning memory with configurable maximum tracked keys (default 10,000) prevents denial-of-service from IP spoofing or memory exhaustion.

---

## 6. Secret Handling & Redaction

* **Configuration**: Secrets are read exclusively from environment variables (`ORION_KNOWN_SECRETS`, or environment variables containing keywords like `API_KEY`, `SECRET`, `PASSWORD`, `TOKEN`).
* **Secret Redaction**:
  * `RedactionEngine` scrubs registered secret strings from all timeline event descriptions, event metadata, and SSE broadcast streams.
  * Replaced with deterministic `[REDACTED]` markers.
  * Strings, nested dictionaries, lists, and tuples are recursively sanitized.
* **Log & Representation Safety**:
  * `AppConfig.__repr__` masks secret values, reporting only count (e.g. `known_secrets=(2 registered)`).
  * Error messages never interpolate raw credentials.
  * Full tracebacks are suppressed in HTTP error responses.

---

## 7. Error Handling Contract

All error paths return a standardized, RFC-compliant JSON payload:
```json
{
  "error": "Descriptive, client-safe error message",
  "code": "ERROR_CODE_ENUM",
  "status": 400,
  "timestamp": "2026-10-03T01:30:00Z"
}
```
* **No Traceback Disclosure**: Internal Python tracebacks (`Traceback (most recent call last)`) are never returned in client HTTP responses.
* **Dual Field Compatibility**: Both `error` and `status` fields are retained at top level to ensure existing Phase 7 frontend and integration test contracts remain intact.

## 8. Health, Readiness & Observability

### Liveness Probe (`GET /api/v1/health` and `/api/health`)
* Returns `HTTP 200 OK` when the HTTP server process is running.
* Reports `uptime_seconds`, `version`, and `missions_count`.

### Readiness Probe (`GET /api/v1/readiness` and `/api/readiness`)
* Verifies operational readiness before routing client traffic:
  1. Service is running and not in the process of shutting down.
  2. Workspace directory exists and is accessible.
  3. Workspace filesystem is actively writable (verified via atomic touch/unlink probe).
* Returns `HTTP 200 OK` with `status: "ready"` when all checks pass.
* Returns `HTTP 503 Service Unavailable` with `status: "not_ready"` if shutting down or if workspace is unwritable.

## 9. Graceful Shutdown Lifecycle

* **Signals**: Registers handlers for `SIGINT` (Ctrl+C) and `SIGTERM` (Docker / container orchestrators).
* **Service Lifecycle Order**:
  1. `service.shutdown()` is called:
     - Sets internal `_is_shutting_down = True` (immediately causes readiness probe to fail with 503).
     - Transitions all non-terminal in-flight missions to `SHUTDOWN` status and records `Server shutting down` error.
     - Broadcasts `SYSTEM_SHUTDOWN` event across all active SSE subscriber queues.
     - Clears subscriber queues to allow client listener threads to terminate cleanly.
  2. `server.shutdown()` halts socket accept loops without aborting in-flight transfers.
  3. `server.server_close()` frees the TCP port.
* **Mission State Preservation**: In-flight missions are never left in ambiguous or corrupted states. They are marked `SHUTDOWN` with deterministic records.

---

## 10. SSE Reliability & Frontend Handling

* **Keepalive Pings**: Server sends `: keepalive\n\n` comments every second when event queues are idle, preventing proxy timeouts.
* **Disconnection Cleanup**: Broken client sockets (`BrokenPipeError`, `ConnectionResetError`) trigger immediate unregistration of the queue from `MissionRecord.subscribers`.
* **Clean Termination**: SSE event loop terminates on `TASK_COMPLETED`, `TASK_TERMINATED`, and `SYSTEM_SHUTDOWN`.
* **Client Backoff**: Frontend client uses exponential backoff on connection drops and displays real server connectivity state without fabricated progress.

---

## 11. Docker & Deployment Hardening

* **Non-Root Execution**: Runs under unprivileged user `orion` (UID/GID 1000).
* **Explicit Signal**: Dockerfile specifies `STOPSIGNAL SIGTERM` for fast container shutdown.
* **Built-in Healthcheck**: Docker container runs non-external healthcheck using Python's standard library `urllib` against `/api/v1/health`.
* **Zero Secret Baking**: Image contains no credentials or `.env` files.
* **Compose Integration**: `docker-compose.yml` mounts local data into `/workspace:rw`, sets `ORION_ENV=production`, and handles `stop_signal: SIGTERM`.

---

## 12. Known Limitations & Scope Boundaries

* **Single-Node In-Process Rate Limiter**: Rate limiting is currently managed in-process via token buckets. For clustered/multi-replica deployments (future phases), a distributed cache like Redis would be required.
* **In-Memory State Default**: Mission state and approval tokens are currently stored in memory per server instance. Long-term persistent database backing is deferred to later milestones.
* **Phase Invariants**: No Phase 9 benchmarking or Phase 10 features have been introduced.
